# 规则引擎技术选型记录

> 类型：项目技术决策记录（ADR）
> 状态：首期方案已实现；存储和运行架构仍可演进。

## 当前决策

首期使用 Go 自有领域模型和 JSON 条件 DSL，不引入完整第三方规则平台。目标是先稳定规则数据模型、管理 API 和可验证的确定性求值流程。

| 层 | 当前选择 | 当前边界 |
|----|----------|----------|
| DSL | Go struct 对应 JSON 规则集与递归条件树 | 尚无独立 JSON Schema 文件或版本迁移工具 |
| 条件求值 | `internal/engine/evaluator` | 支持 `all`、`any`、`not` 与内置比较操作符 |
| API | Go 标准库 `net/http` / `ServeMux` | 适合当前 API 规模；尚未引入独立 API gateway 服务 |
| 存储 | PostgreSQL 实体表仓储 | 重启可恢复；进程内缓存要求单 API 副本；Redis 不参与规则存储 |
| 管理端 | React + TypeScript + Vite | 画布和 JSON 双模式，共用 OpenAPI 生成的 SDK |
| 执行动作 | 决策响应中的声明数据 | 没有 Webhook、变量修改或其他外部副作用 |

## 为什么先采用 JSON 条件树

- 与管理端和 HTTP API 的数据形态一致，便于存储、传输和可视化编辑。
- `all`、`any`、`not` 递归组合可以明确表达首期条件逻辑。
- 将条件校验、求值和业务编排分开，未来替换存储实现时不必绑定具体 ORM 或数据库。
- 先保留小而明确的运算符集合，等需求出现后再讨论表达式语言、函数、变量和决策表。

## 后续评估项

持久化方案需结合规则版本、并发写入和备份要求评估；缓存需要真实性能基线和失效策略；分离计算集群需要稳定的发布与运行契约。AI 条件、动作插件、决策表和异步任务都尚未在当前领域模型中实现，不能仅凭环境配置字段视为已有集成。
