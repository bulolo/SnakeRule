# 规则生命周期与运行观测方案

## 当前情况

- 规则集现在直接保存可编辑内容；规则求值读取已保存规则集，没有独立的草稿、发布快照或回滚版本。
- 调用日志已保存请求/响应预览、求值结果、命中规则、来源和耗时，并提供项目内分页详情；保留量目前是固定上限，尚无按时间配置的清理策略。
- 条件模型支持 `all`、`any`、`not` 嵌套组合，后端执行条件校验。条件画布已有组合编辑基础，但应补齐按事实类型呈现操作符语义、节点级错误定位和无效草稿防保存。
- 概览中的调用统计来自调用日志。还没有完整的服务级指标采集与告警体系。
- 仓储通过进程内聚合缓存并整组同步数据库；在仓储并发安全完成前，不应把本方案误解为支持多 API 副本。

## 目标数据模型

新增 `ruleset_versions`，字段至少包括：

| 字段 | 作用 |
| --- | --- |
| `id` | 不可变版本 ID |
| `ruleset_id` | 所属规则集 |
| `version_number` | 规则集内单调递增序号，唯一约束为 `(ruleset_id, version_number)` |
| `snapshot` | 发布时完整规则集 JSONB 快照 |
| `content_hash` | 规范化快照摘要，用于识别相同内容 |
| `created_by`、`created_at` | 发布者与发布时间 |
| `change_note` | 可选发布说明 |

规则集增加 `published_version_id`。发布时在一个数据库事务内校验草稿、写入新快照并更新当前发布指针；已写入的快照禁止更新或删除。回滚是将历史快照复制为新的版本并移动发布指针，保留完整审计链。规则集草稿仍可继续编辑，在线求值只读取当前发布快照。管理端模拟可明确选择“草稿”或“当前发布版”，并在结果中展示求值版本。

新增版本变更审计记录，至少记录组织、项目、规则集、版本 ID、操作人、动作（发布/回滚）、时间和说明。密钥、认证头和敏感事实值不得进入审计内容。

## 决策记录与保留

调用日志补充 `ruleset_version_id`、唯一 `request_id` 和明确的 outcome 字段。分页查询支持：时间范围、规则集、发布版本、成功/未命中/错误、设计器模拟/真实 API/管理会话、请求 ID。详情继续分开展示概览、请求、响应和命中规则。

保留期用服务端配置控制，按批次删除过期记录并记录删除数量、耗时和失败状态。默认值应在配置文档中明确；关闭或设为零的语义也要明确。不能仅依赖固定条数上限，因为高低流量项目会得到完全不同的保留时长。保留策略上线时说明它仅影响调用记录，不影响规则版本和审计记录。

## 服务级指标

先确定低基数指标，禁止把用户输入、项目 ID、规则集 ID、API Key 或请求 ID 用作标签：

- HTTP 请求数与状态码类别、路由模板、方法。
- HTTP 请求时延直方图。
- 规则求值次数、结果类别与求值耗时直方图。
- 数据库连接池使用量、等待数，以及就绪状态。
- 进程启动时间和构建版本信息。

通过 Prometheus 兼容端点供采集系统抓取；不要在应用里自行计算或存储 p95/p99 时序数据。Prometheus 使用直方图计算分位数。指标端点的访问范围在 Compose/Helm 部署中配置；生产环境不应默认暴露到公网。管理端如需展示运行指标，应消费有明确时间范围和采集来源的聚合接口；缺少采集器或数据时显示无数据状态。

最小告警规则包括 API 不可用、错误率持续升高、p95 延迟超阈值、数据库连接耗尽和迁移失败。阈值在性能基线建立后确定，不预填没有依据的承诺值。告警路由复用平台现有告警渠道时，须区分基础设施告警与规则命中通知。

## 分阶段交付

### 阶段一：决策契约和可验证基线

- 明确 draft/published 求值语义及版本字段，更新 OpenAPI，再生成 SDK。
- 增加发布快照、并发发布保护和事务边界测试；测试回滚创建新版本且旧快照不变。
- 将调用记录与发布版本关联；补齐结果类型、来源、请求 ID 的筛选和详情测试。
- 为所有现有条件操作符建立语义表和测试矩阵，涵盖类型不匹配、缺失值、null、嵌套、空分组。

### 阶段二：管理端流程

- 编辑器始终编辑草稿；提供校验、发布说明、版本历史、差异查看及回滚确认。
- 求值/API 调用固定使用已发布版本，并在日志中显示实际版本；设计器可显式运行草稿。
- 条件画布按事实类型限制可用操作符，错误显示在对应节点，键盘操作和返回路径可用。

### 阶段三：记录保留与运行指标

- 新增可配置调用日志保留期和可观测的分批清理任务。
- 接入 Prometheus 指标、抓取配置、最小告警规则，并在 Docker Compose 与 Helm 暴露可选配置。
- 为指标端点补充权限/网络边界说明；不采集高基数或敏感标签。

### 阶段四：性能基准与优化决策

- 提供固定数据集与可重复的压测脚本，分别覆盖纯求值、完整 API、日志写入和多规则集读取。
- 记录硬件/容器资源、数据库版本、配置、规则规模、并发、吞吐、p50/p95/p99、错误率和资源使用。
- 依据测试瓶颈评估索引、缓存和规则热更新；每次优化保留前后对比数据及正确性测试。

## 完成标准

- API 运行时只使用不可变已发布快照；没有发布版本的规则集行为明确且不会静默执行未发布草稿。
- 回滚生成新版本，审计可追溯，OpenAPI 和 SDK 一致。
- 调用日志可按上述条件分页检索，详情能定位实际规则版本，保留清理经过测试。
- Prometheus 指标可被抓取，部署模板能显式启用/限制端点，管理端不伪造指标。
- 有可重复的性能基准报告；优化依据基准数据而不是主观猜测。
- PostgreSQL 集成测试、后端测试、管理端/文档构建和生成 SDK 一致性检查纳入 CI。

## 当前范围建议

先做阶段一，之后再改默认求值语义和管理端流程。不可变版本、数据库事务、权限审计及 API 契约要同时设计，避免先做只存在于界面的“发布”状态。阶段三可与阶段二并行设计，但清理任务和多副本部署应等待仓储并发安全完成。性能优化明确排在基准测试之后。
